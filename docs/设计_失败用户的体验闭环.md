# 设计：失败用户的体验闭环 —— 让"没解决"也不流失

> 核心命题：用户可以带着"没解决"离开，但绝不能带着"这东西没用"离开。
> 本文写的不是功能逻辑，是**用户在每个时刻真正读到的字**——心态是靠这些字护住的。

---

## 0. 要消灭的两种心理，要建立的一种感觉

| 要消灭 | 典型心声 | 后果 |
|---|---|---|
| **失望型流失** | "试了三次都不行，这东西没用" | 再也不来 |
| **被利用感** | "合着我是来帮你训练模型的" | 不但流失，还说坏话 |

| 要建立 | 表现 |
|---|---|
| **"它真的在帮我"** | 即使这一局没赢，它也一直在出力、一直有下一步、一直有人接 |

---

## 1. 核心洞察：用户流失不是因为"没解决"，是因为"没盼头"

一个人可以接受失败三次。
他不能接受的是：三次失败之后，**不知道有没有第四次、第四次和前三次有什么区别**。

所以产品的承诺不该是"一定解决"，而是——

> **永远给你下一步，且下一步比上一步更接近答案。**

**愿意跟进 = 看得见的进展 + 确定存在的下一步。**

---

## 2. 三个心态危险时刻

| 时刻 | 用户心里的话 | 错误做法 | 正确做法 |
|---|---|---|---|
| 第一次没做成 | "果然不行" | 弹一个"操作失败" | 立刻追问定位——让用户觉得"开始排除"了，而不是"结束了" |
| 连续没做成 | "这就是个套壳 GPT" | 硬出第 4 版方案 | 承认边界、切换策略，并**解释为什么切换** |
| 判定需要求助 | "要我自己去发帖？那要你干嘛" | 甩个链接让用户自己问 | 产品替他把帖子写好、发好、盯好 |

---

## 3. 五个关键时刻的界面文案（可直接用的微文案）

### 时刻 1｜第一次没做成

```
卡点了？告诉 AI 卡在哪一步——是报错，还是现象和预期不符？

  [ 第 3 步报错 ]  [ 现象不对 ]  [ 其他 ]

别急。排除一个方向，也是进展。
```

**设计意图**：全文不出现"失败/错误/无法"；把反馈包装成"缩小范围"，让用户从"被评判者"变成"共同排查者"。

---

### 时刻 2｜连续没做成

```
连续两条路都不通——这恰恰说明你的场景比原帖特殊得多。

AI 正在换思路：从"照搬原帖"切换到"基于你的约束重新设计"。

✗ 已排除：中断直收、DMA 双缓冲
→ 剩余可试：软件分层缓冲、降速 + 校验重传
```

**设计意图**：把"重复失败"重新解释为"你的场景更特殊"（是场景难，不是 AI 差）；
用"已排除 / 剩余可试"展示棋盘——**用户看见的是棋盘，不是墙**。

---

### 时刻 3｜判定需要求助（全场最关键的一段话）

```
你的问题很有价值，但也确实超出了现有经验的覆盖范围。

这 3 条路、2 个卡点，我们已经帮你整理成一份完整的求助材料——
比你自己从头写，要完整得多。

接下来，让真正踩过这个坑的人接手。
我们继续帮你盯着，一有回应就通知你。
```

**设计意图（逐句拆）**：
- "你的问题很有价值" → 先定性：不是 AI 不行，是这个问题本身就难
- "超出现有经验的覆盖范围" → 诚实承认边界，**反而**让用户觉得前面那些方案可信
- "已经帮你整理成材料" → 产品的价值在最后一公里也在体现
- "让踩过坑的人接手" → 求助不是降级，是升级：接入更高级的智慧
- "我们继续帮你盯着" → **产品不退场**，这一句是留住"愿意跟进"的关键

---

### 时刻 4｜求助帖生成后，让用户看见质量

```
这条求助，是按"最容易被回答"的方式组织的：
处境 / 约束 / 已试方案 / 卡点，一目了然。

比起随手提的问题，这样的帖子被有效回答的概率高得多。
[ 预览 ]  [ 发到原帖评论区 ]  [ 发到圈子 ]
```

**设计意图**：让用户亲眼看到"这段材料比我写的强"——
他会意识到：**即使 AI 没解决问题，它也已经替我完成了最难的部分。**

---

### 时刻 5｜后续每一次进展（让"跟进"有回报）

```
🔴 有人回应你的求助了 → 查看
🟢 你标记的"此路不通"，已经帮 12 个人避开 → 查看
```

**设计意图**：通知必须**具体**（不是"有新动态"）；
"帮 12 个人避开"这条同时完成了身份升级——**他从提问的人，变成了给后来者立路标的人。**

---

## 4. AI 替用户生成的求助帖（模板）

AI 生成的不是"求救信号"，是一份**结构化的技术求助**。模板：

```markdown
【求助】G3507 双串口并发收摄像头 + 蓝牙，DMA 配置后仍丢帧

## 我的处境
- 主控 MSPM0G3507；摄像头 115200 持续流 + 蓝牙 9600
- 约束：不能换主控，工期 3 天

## 参考的解法
来自《STM32 串口通信踩坑全记录》（原帖场景：F103 + 单摄像头）

## 已试 3 条路，都卡住了
1. ✗ 直接沿用原帖的中断收发 → 高速流持续丢帧
2. ✗ 开 DMA 双缓冲 → 每 512 字节丢 1~2 字节
3. ✗ 降低蓝牙波特率 → 无改善

## 当前卡点
怀疑是 DMA 通道仲裁配置问题，但 G3507 手册和 F103 不一致，
找不到对应寄存器。

## 想请教
- 有没有在 G3507 上跑通过双串口 DMA 的？
- 或者指条路：这个场景是不是本就该换思路（如软件分层缓冲）？
```

**这份东西的价值**：用户自己在知乎提问，通常只能写出"为什么我的串口丢数据？"——
而这份材料里有处境、有约束、有已排除项、有具体现象。
**哪怕 AI 没解决问题，它也已经把用户完成了 80%。** 这就是"它真的在帮我"的实感来源。

---

## 5. 底层原则（三条铁律）

1. **不出现"失败"** —— 只有"排除了一个方向""这条路不通""换个思路"
2. **每次反馈都伴随"我们学到了什么"** —— 让用户看见进展，而不是原地打转
3. **永远给出下一步** —— 换方向 / 补信息 / 找人，三选一，从不给死胡同

---

## 6. 对应要做的功能（MVP 缺口，按优先级）

| 优先级 | 功能 | 对应时刻 |
|---|---|---|
| P0 | 失败反馈入口（做成了/没做成 + 卡点选择） | 时刻 1 |
| P0 | 归因追问（AI 追问一句，三分归因） | 时刻 1→2 |
| P1 | v2 迭代（上下文已在，AI 换思路重出方案） | 时刻 2 |
| P1 | 求助帖自动生成（处境+已试+卡点 → 结构化材料） | 时刻 3、4 |
| P2 | 一键分发（原帖评论 / 圈子）+ 回复通知 | 时刻 5 |
| P2 | "此路不通"节点标记（蛛网上红色节点，含避开了多少人） | 时刻 5 |
